# Этапы 6–7. Проверка и отдача

## Проверка руками

Открой прототип в браузере и пройди главный сценарий как пользователь, а не как
автор. Читать код недостаточно: почти всегда находится кнопка, которая ведёт
в никуда, потому что экран переименовали, а обработчик — нет.

Если доступны браузерные инструменты (`preview_start`, затем `navigate` и
`computer`), кликай ими и смотри консоль на ошибки. Если нет — попроси человека
открыть файл и пройти сценарий, назвав шаги по порядку.

### Что проверить

**Навигация**
- [ ] Каждый пункт меню открывает свой экран, заголовок в шапке меняется
- [ ] Переключение ролей перестраивает меню и открывает стартовый экран роли
- [ ] Из карточки есть возврат в список
- [ ] Ни один элемент, похожий на кнопку, не молчит при нажатии

**Главный сценарий**
- [ ] Проходится от начала до конца без тупиков
- [ ] Мастер пускает назад на пройденные шаги, введённое не теряется
- [ ] Валидация срабатывает и объясняет, что не так
- [ ] Финал сценария виден: договор, подтверждение, запись в списке

**Данные**
- [ ] После обновления страницы числа те же самые
- [ ] Даты живые относительно `TODAY`, ничего не выглядит просроченным случайно
- [ ] Суммы отформатированы по-русски: `62 000 ₽`, а не `62000`
- [ ] Главная боль видна на первом экране без объяснений

**Тексты**
- [ ] Нет «Lorem ipsum», «Заголовок», «Кнопка», «Текст»
- [ ] Термины — из словаря клиента, а не общие
- [ ] У каждого пустого состояния свой осмысленный текст
- [ ] Прогнано через `proofreader-ru`, если доступен

**Внешний вид и доступность**
- [ ] Длинное имя и длинное название не ломают таблицу
- [ ] Фокус виден при переходе табуляцией
- [ ] Статус читается не только по цвету, но и по подписи
- [ ] В консоли браузера нет ошибок

### Скиллы на этом этапе

- `/critique-screen` из `visual-critique` — обязательно, по двум-трём ключевым
  экранам. Даёт список правок по приоритету; на прототипе имеет смысл брать
  верхнюю треть и не увлекаться остальным.
- `prototyping-testing:heuristic-evaluation` — если прототип пойдёт на тест
  с пользователями.
- `design-systems:accessibility-audit` — если заказчику важна доступность.
- `ux-psychology-review` — если прототип должен убеждать, а не только показывать.

Не тащи в прототип все найденные правки. Прототип живёт неделю; вылизывать
отступы в нём — потраченное время. Чини то, что мешает пройти сценарий или
портит первое впечатление.

## Отдача

### README

На русском, коротко. Человек будет пересылать его вместе со ссылкой.

```markdown
# Название — кликабельный прототип

Одно-два предложения: что это и для кого.

Один самодостаточный HTML-файл без зависимостей — `index.html`.
Откройте его в браузере двойным кликом или разверните на любом
статическом хостинге.

## Роли

Переключаются через меню под именем пользователя внизу левой панели.

- **Администратор точки** — Аренда (мастер оформления, карточка,
  продление, приёмка возврата), Велосипеды, Перемещения.
- **Менеджер по каналам** — Остатки по всем точкам сети.

## Что не входит

Прототип для демонстрации: данные живут в памяти страницы и
сбрасываются при обновлении, авторизации и сервера нет.
```

Раздел «что не входит» экономит неловкий разговор на встрече, когда заказчик
спросит, почему введённое пропало.

### Git

```bash
git init
git add -A
git commit -m "Кликабельный прототип: роли администратора точки и менеджера"
```

Дальше — по одному коммиту на осмысленную порцию правок. Человеку без опыта в
коде git нужен ровно за одним: вернуться к версии, которая работала, когда
правки на встрече завели не туда.

### Ссылка

Два варианта, спроси у человека, какой удобнее:

- **GitHub Pages** — репозиторий, `Settings → Pages → Deploy from branch`,
  ссылка вида `https://<логин>.github.io/<репозиторий>/`. Живёт долго,
  обновляется push-ем.
- **Публикация артефактом** — быстрее, ссылка сразу, ничего настраивать не надо.
  Подходит, когда показать нужно сегодня. Файл при этом всё равно остаётся
  у человека на диске.

Ссылка по умолчанию приватная. Прототип с данными клиента никуда не выкладывай,
не спросив.

### Если прототип идёт дальше

- В разработку — `design-ops:handoff-spec` соберёт спецификацию по экранам.
- На защиту решения — `designer-toolkit:design-rationale` объяснит, почему
  сделано так, а не иначе.
- В презентацию — `designer-toolkit:presentation-deck`.
